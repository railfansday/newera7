Home Server Recovery and a Weekly Clone: Blog Post and Reproduction Runbook

Tanggal: 2026-11-03

Replace every with your own values. Never paste secrets (passwords, API keys, tokens) into a chat.

This home server has two NVIDIA GPUs in one machine. An RTX 3060 runs local LLM inference: a 12B quantized model served by llama.cpp as a systemd service. An RTX 3070 mines while the machine is idle. The system originally ran from a single 500 GB SATA hard disk, which held the OS, the models, and all service data.

This post covers the migration, the update that exposed the lack of a fallback, and the weekly clone that now keeps the spare current.

Why the hard disk was expected to be the bottleneck. The services on this machine issue many small reads: Python imports, shared libraries, systemd units, and the model file. On a mechanical disk, those reads are bound by seek latency. NVMe removes most of that latency.

Results. I did not record benchmarks before or after the migration, so this post makes no numeric claims about speed. Subjectively, the improvement was noticeable for only a few days before it became the new normal. The lesson: if performance is the goal, record a baseline before the change, not after it.

Gotcha. The old disk still held a complete, valid system. If its old UUID stayed in fstab as a writable mount, the next boot would try to mount it. Remove the entry, or mark it nofail and read-only.

A routine system update went wrong partway through, and the primary disk could no longer be trusted to keep running as before. The spare was not bootable, so I had no working fallback. Closing that gap is the point of this post.

The clone is a single generation. A bad change on the primary reaches the spare on the next run. This is deliberate: the clone guarantees a bootable copy of the latest state, not a history.

このマシンには NVIDIA GPU を 2 枚載せている。RTX 3060 はローカル LLM の推論に使う。12B の量子化モデルを llama.cpp で動かし、systemd のサービスとして提供している。RTX 3070 は、アイドル時にマイニングへ回す。当初は 500GB の SATA ハードディスク 1 台で動かしていて、OS もモデルもサービスのデータもすべてそこに載っていた。

ボトルネックと想定した理由。 このマシンのサービスは、Python の import、共有ライブラリ、systemd のユニット、モデルファイルなど、小さな読み込みを大量に行う。機械式ディスクでは、これらがシーク時間に左右される。NVMe にすれば、そのレイテンシは大きく減るはずだった。

結果。 換装前後のベンチマークは記録していない。したがって、この記事では速度について数値による主張はしない。体感の改善は数日で薄れ、以降は当たり前の状態になった。性能が目的なら、変更の前にベースラインを記録しておくこと。後から測っても、比べられない。

注意点。 古いディスクには、動く完全なシステムが残っている。古い UUID のまま書き込み可能なマウントとして fstab に残すと、次の起動でそれをマウントしようとする。エントリを削除するか、nofail と読み取り専用にすること。

更新の途中で、主ディスクをこれまでどおりには信用できなくなった。予備ディスクは起動できない状態だったから、フォールバックがなかった。このギャップを埋めるのが、この記事の目的だ。

単独で起動できる第二のシステムが必要だったので、予備ディスクの root パーティションをフォーマットし、動いているシステムを丸ごとコピーした。

ファームウェアの起動メニューから予備ディスクを選ぶと、クローンしたシステムが立ち上がった。期待している経路だけでなく、すべての読み込み経路を確認すること。ここを省くと、あとで必ず痛い目を見る。

一度きりのクローンは、そのあとの変化を守ってくれない。そこで、動いている主ディスクの root を予備に毎週ミラーするジョブを追加した。

クローンは世代を持たないので、主ディスクで壊れた変更は次の同期で予備にも反映される。これは意図的なトレードオフだ。クローンが保証するのは「最新の状態を起動できるコピー」であって、履歴ではない。
