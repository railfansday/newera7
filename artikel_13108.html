Getting Past Google Apps Script's 6-Minute Limit and n8n Out-of-Memory Crashes

Tanggal: 2026-11-03

I build Google Sheets and Apps Script tools alongside small Python services, and I keep running into the same two walls as row counts grow.

The first is the 03:06 AM Google Sheets failure email. An internal Google Apps Script that synced 400 orders or CRM leads in January now has 8,500 rows to process. Google kills the morning run halfway through with Exceeded maximum execution time. The script stops with half the spreadsheet updated, after firing duplicate API webhooks and breaking formulas.

The second wall is a quiet n8n container restart on a 2 GB or 4 GB VPS. A self-hosted n8n workflow runs SplitInBatches over a 15,000-row CSV or Shopify catalog and dies with Exit Code 137 or FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory.

Teams respond by renting more VPS RAM for n8n or splitting a Google Sheet across five tabs. Both workarounds buy a little breathing room while leaving the real bottlenecks intact: per-cell network round trips and growing execution state.

Google's V8 Apps Script sandbox and n8n's Node.js worker fail in different places, though both punish row-by-row loops:

In Apps Script, each getValue() or setValue() call crosses an internal network boundary to Google Sheets. At 80 to 150 ms a call, 3,000 setValue() writes eat most of your 6-minute budget on round trips alone.

You can batch outbound HTTP traffic the same way. Pass an array of request objects to UrlFetchApp.fetchAll(requests) and Google runs those requests in parallel on its own infrastructure:

Batched reads and writes hit the same 6-minute limit once a sheet holds 45,000 rows or calls a slow external ERP API that needs 25 minutes end to end. Checkpointing does not lift the daily quota either: a consumer account gets 20,000 UrlFetchApp calls per day (100,000 on Workspace), so a job that calls an API for every row of a 45,000-row sheet has to spread over more than one day on a consumer account.

Do not wait until second 359 for Google to kill the script mid-write. Set a soft wall-clock budget of 270 seconds (4.5 minutes) and save cursor_row in PropertiesService.getScriptProperties() after each batch. Before exiting, clear old continuation triggers to prevent duplicate trigger storms, then schedule a single trigger to resume 60 seconds later:

You also want a lock on doPost(e) webhook receivers. Wrap the write in const lock = LockService.getScriptLock(); lock.waitLock(15000); try { ... } finally { lock.releaseLock(); }. The overwrite happens when the handler computes its target row with getLastRow() + 1 and then calls setValues(): 5 Stripe or Shopify webhooks arriving in the same second can all read the same last row. The lock also covers any read-then-write logic, such as checking for a duplicate order ID before appending.

A 2 GB self-hosted n8n instance can crash on a 12 MB JSON payload or a 5,000-row SplitInBatches loop because its execution engine snapshots output items at each node boundary. Those snapshots let the UI canvas render intermediate outputs and resolve expressions like $('Previous Node').item.json. Pass a 12 MB array through 8 transformation nodes in one execution and V8 ends up holding several serialized copies, eating hundreds of MB of heap.

Keeping SplitInBatches inside one monolithic workflow compounds the problem. The parent execution holds onto previous batch iterations in its memory tree until the entire run finishes.

In your docker-compose.yml or .env for self-hosted n8n, switch binary handling off default (RAM) if your workflows touch CSV exports, PDFs, audio files, or scraped HTML snapshots:

Setting EXECUTIONS_DATA_SAVE_ON_SUCCESS=none on high-volume worker workflows stops n8n from serializing 100 MB JSON execution blobs into SQLite or Postgres at completion.

Once the child sub-workflow finishes and hands back that 32-byte summary, V8 can garbage-collect the child execution's intermediate data before batch #2 starts. The process holds one batch in memory at a time instead of growing with the total row count.

n8n fits stateful orchestration and webhook routing, while 5,000-URL crawls and fuzzy CSV deduplication bog down its Node worker.
